# CLAUDE.md — Project Agent Guide

> Generated by quantum-lens. This file is loaded into every quantum-loop iteration
> (including each parallel worktree agent). Keep it tight and imperative.

## Build & verify commands (authoritative)

Read these from `lens.config.json`. Do not invent commands.

- Typecheck: see `gates.typecheck`
- Lint: see `gates.lint`
- Unit tests: see `gates.unit`
- E2E: see `gates.e2e`
- **Visual gate (UI work only): `bash verification/run-visual-gate.sh <route>`**

## The Iron Law (inherited from quantum-loop, do not weaken)

No completion claim without **fresh** command output proving it. "Should work",
"probably passes", and "passed earlier" are not evidence. Run the command this
iteration, read the full output, then assert.

## The Pixel Law (quantum-lens extension)

A passing test suite does **not** mean the UI is correct. For any story that
renders UI, "done" additionally requires the visual gate to pass:

1. Visual-regression screenshots match the approved baseline within tolerance.
2. Zero accessibility violations (axe) at every configured breakpoint.
3. Lighthouse scores meet the thresholds in `lens.config.json`.

If there is no approved baseline yet, generate one, **render it, look at the
screenshot**, and confirm it matches `DESIGN-SYSTEM.md` before blessing it as the
baseline. A baseline you never looked at is not a baseline.

## Design discipline

- Every visual decision derives from `DESIGN-SYSTEM.md`. Use the token names
  exactly (they are also `contracts` in quantum.json — deviating is a halt-and-propose event, never a silent change).
- No generic AI aesthetics: no Inter/Roboto/Arial defaults, no purple-gradient-on-white,
  no cookie-cutter card grids unless the design system explicitly calls for them.
- Match implementation effort to the aesthetic: maximalism needs elaborate code;
  minimalism needs precision in spacing, type scale, and motion.

## Approval rules (brainstorm/spec/plan walkthroughs)

Never ask the user to approve content they cannot see — and never make them read
it inside a question widget. The pattern:

1. Present the section as a normal, well-formatted markdown **message**: a `##`
   heading, a short lead sentence, then `- Label: choice` bullets for the
   decisions. Scale length to complexity — a few sentences when simple, 200–300
   words max when nuanced. Visible output, not thinking, not only a file write.
2. THEN ask a lightweight approval question in the same turn. One line, pointing
   at what's above ("Section 2 — UX (shown above): approve?"), with options like
   Approved / Needs changes. Do NOT cram the section content into the question
   text or option descriptions — it lives in the message directly above.
3. After all sections are approved and the doc is written, ask the user to
   review the **written file** before proceeding ("Design written to `<path>` —
   please review it before we continue to the next stage").
4. An approval given without the content on screen is not an approval. Re-present
   and re-ask.

## Parallel-execution rules

- You may be one of several agents running in isolated worktrees. Touch only the
  files your story owns (the union of its tasks' `filePaths`). If you need a value another
  story produces, read it from the `contracts` section of quantum.json — never guess.
- **Stay inside your declared `filePaths`.** Parallel waves only work because same-wave stories
  touch disjoint files; quantum-loop's filter (which aggregates `tasks[].filePaths`) serializes
  any that overlap. If you find you must edit a file another story owns, stop and surface it —
  do not silently expand your footprint, or you'll collapse the wave's parallelism (or cause a
  merge conflict).
- Commit before signaling completion (`git add -A && git commit`). Uncommitted
  work in a removed worktree is lost.
- One story per context window. Do not opportunistically fix unrelated things.

## Anti-rationalization (these excuses are forbidden)

| If you catch yourself thinking... | The truth is... |
| --- | --- |
| "Tests pass, so the UI is fine"   | Tests don't render pixels. Run the visual gate. |
| "It's a tiny style tweak, skip the baseline" | Tiny tweaks are exactly what visual regressions catch. |
| "Close enough to the design"      | Use the exact token. Close enough is a visual bug. |
| "I'll add the a11y labels later"  | Later means never. The a11y gate blocks the commit now. |
| "The screenshot looks right to me" | Looking is advisory. The diff/axe/lighthouse output is the gate. |
